MOTION STUDIO V2 — OPENCODE CONSTRUCTION SPECIFICATION

This is the rebuild specification for the previous Build.txt / Version 0 foundation.

This document is not a conceptual essay. It is a construction specification intended to be executed by OpenCode.

The target is a professional, agent-operated motion-design studio where the human acts as creative director and final approver, not as a repair technician.

───

EXECUTIVE ARCHITECTURE

The studio is organized as a layered production system.

text
CLIENT BRIEF
    ↓
HUMAN CREATIVE DIRECTION
    ↓
OPENCODE ORCHESTRATOR
    ↓
TASK GRAPH / AGENT SWARM
    ↓
RESEARCH / REFERENCE / STYLE / DESIGN / MOTION / ASSETS / IMPLEMENTATION / QA
    ↓
MOTIONSPEC
    ↓
MOTION IR
    ↓
RENDERER ADAPTER
    ↓
EXECUTION ENGINE
    ↓
RENDER / INSPECT / QA
    ↓
HUMAN CREATIVE REVIEW
    ↓
LOCALIZED REVISION
    ↓
FINAL DELIVERY


The most important architectural rule is:

text
Creative intent is the source.
MotionSpec is the structured creative contract.
Motion IR is the canonical machine-readable motion representation.
Renderers are execution backends, not sources of truth.


The studio must support:

• 2D motion graphics
• typography
• graphic design
• compositing
• camera language
• procedural animation
• data-driven animation
• 2D/3D hybrid work later
• editorial assembly
• client-specific visual systems
• reusable motion primitives
• reference analysis
• iterative creative direction
• technical and visual QA
• accumulated validated knowledge

The human should be able to say:

“The opening needs to feel more premium and restrained. Keep the composition but make the impact 20% heavier and let the typography breathe longer.”

The system should translate that into:

text
style.energy: reduce
behavior.impact: +20%
typography hold: increase
recovery: slower
camera reaction: softer
negative: avoid extra decoration


and then produce a localized implementation patch.

The human should not need to say:

“Change layer 17 position from 840 to 817 and adjust the third keyframe.”

KEY ARCHITECTURAL DECISIONS

Each major decision below includes:

• DECISION
• WHY
• EVIDENCE
• ALTERNATIVES CONSIDERED

• IMPLEMENTATION CONSEQUENCE

───

ADR-001: Renderer is not source of truth

DECISION

The renderer is an execution backend. Motion IR is the canonical representation.

WHY

If HyperFrames, Remotion, Fusion, or GSAP becomes the source of truth, creative intent becomes trapped in implementation details.

EVIDENCE

The studio must support multiple renderers and preserve creative meaning across revisions.

ALTERNATIVES CONSIDERED

1. Store scenes directly as HyperFrames code.
2. Store scenes directly as Remotion components.
3. Store scenes directly as Fusion node graphs.

WHY ALTERNATIVES WERE REJECTED

They couple creative intent to one backend and make renderer migration expensive.

IMPLEMENTATION CONSEQUENCE

All generated renderer code must be traceable back to a MotionSpec and Motion IR.

───

ADR-002: Use real HyperFrames, not internal reimplementation

DECISION

Use real HyperFrames through an adapter. Do not recreate HyperFrames inside the studio.

WHY

HyperFrames already targets deterministic HTML/CSS/media-to-video rendering and agent workflows.

EVIDENCE

The rebuild directive explicitly identifies HyperFrames as an actual open-source framework with CLI capabilities.

ALTERNATIVES CONSIDERED

1. Continue with internal Playwright/esbuild renderer.
2. Build a custom deterministic browser renderer.
3. Use Remotion for everything.

WHY ALTERNATIVES WERE REJECTED

1. Internal renderer duplicates infrastructure.
2. Custom renderer increases maintenance burden.
3. Remotion does not replace all HyperFrames/GSAP choreography needs.

IMPLEMENTATION CONSEQUENCE

The previous internal HyperFrames runtime becomes fallback/legacy only. The primary path is:

text
Motion IR → HyperFrames adapter → real HyperFrames → output


Exact CLI flags must be verified by a capability probe before first render.

───

ADR-003: Beat-based timing instead of frame-only authoring

DECISION

Author motion using beats and semantic timing, then resolve to frames.

WHY

Professional motion is motivated by story, audio, impact, anticipation, and reaction, not only frame numbers.

EVIDENCE

The directive requires story/audio/visual beat abstraction.

ALTERNATIVES CONSIDERED

1. Frame-only timing.
2. Seconds-only timing.
3. Audio-only timing.

WHY ALTERNATIVES WERE REJECTED

Frame-only loses intent. Seconds-only ignores FPS. Audio-only fails when no audio exists.

IMPLEMENTATION CONSEQUENCE

MotionSpec must support beat references. Motion IR resolves beats into frames using FPS, duration, pacing, and dependencies.

───

ADR-004: Relationship-based animation

DECISION

Motion IR must model relationships between objects.

WHY

Professional animation often consists of coordinated behavior: lead, follow, react, counterbalance, absorb.

EVIDENCE

The directive requires leader/follower, reactive, delayed, staggered, counter-motion, coupled, independent relationships.

ALTERNATIVES CONSIDERED

Independent object animation only.

WHY ALTERNATIVES WERE REJECTED

It forces the agent to manually coordinate related motion and produces mechanical results.

IMPLEMENTATION CONSEQUENCE

A creative instruction such as:

“Title hits, underline follows late, background reacts subtly, camera absorbs impact.”

must become one coordinated motion event network, not four unrelated animations.

───

ADR-005: Semantic curve resolution instead of direct easing names

DECISION

Creative descriptors resolve into semantic motion characteristics, then into renderer-specific curves.

WHY

Direct mappings like cinematic = power3.inOut are not meaningful enough for professional motion.

EVIDENCE

The directive explicitly rejects hard-coding creative words into arbitrary easings.

ALTERNATIVES CONSIDERED

1. Fixed easing category map.
2. Raw cubic-bezier authoring only.
3. Spring-only model.

WHY ALTERNATIVES WERE REJECTED

1. Fixed map is too shallow.
2. Raw Bézier authoring is too low-level for creative direction.
3. Spring-only cannot express all motion styles.

IMPLEMENTATION CONSEQUENCE

Build a curve resolver:

text
creative description
→ semantic motion characteristics
→ curve profile
→ renderer-specific implementation


GSAP easing is an execution capability, not the definition of the motion language.

───

ADR-006: Shared root dependencies, not per-project dependency trees

DECISION

Use one shared studio dependency tree where practical.

WHY

The user explicitly does not want:

text
project-a/node_modules
project-b/node_modules
project-c/node_modules


EVIDENCE

Node module resolution searches upward through parent directories. npm workspaces support shared root management.

ALTERNATIVES CONSIDERED

1. Independent npm install per project.
2. NODE_PATH global hack.
3. Automatic npm ci before every task.

WHY ALTERNATIVES WERE REJECTED

1. Wastes disk and creates version drift.
2. NODE_PATH is fragile and not default-friendly.
3. npm ci can unnecessarily delete dependencies.

IMPLEMENTATION CONSEQUENCE

Projects inherit the studio runtime. Project-specific dependency exceptions must be explicit and isolated.

───

ADR-007: OpenCode is the live orchestrator

DECISION

OpenCode is the live orchestration layer.

WHY

The user communicates primarily with OpenCode, and OpenCode supports agents/subagents, model configuration, permissions, and task delegation.

EVIDENCE

The directive states OpenCode officially supports primary agents and specialized subagents.

ALTERNATIVES CONSIDERED

1. Custom external orchestrator.
2. Qwen as live orchestrator.
3. Manual human task dispatch.

WHY ALTERNATIVES WERE REJECTED

1. Duplicate orchestration system.
2. Qwen is architect/spec author here, not live executor.
3. Manual dispatch defeats the studio objective.

IMPLEMENTATION CONSEQUENCE

Agent definitions, permissions, and routing policies must be expressed in forms OpenCode can consume natively or through verified configuration adapters.

───

ADR-008: Artifacts instead of conversational memory

DECISION

Agents communicate through structured artifacts.

WHY

Large conversational dumps are hard to validate, inspect, version, and reuse.

EVIDENCE

The directive requires schemas, validation, and inspectable artifacts.

ALTERNATIVES CONSIDERED

Chat-only agent communication.

WHY ALTERNATIVES WERE REJECTED

It creates opaque state and prevents reliable QA.

IMPLEMENTATION CONSEQUENCE

All important agent outputs must be schema-validated artifacts.

───

ADR-009: Controlled knowledge promotion

DECISION

Agents may propose lessons, but permanent knowledge requires validation and promotion.

WHY

Uncontrolled learning can poison client/studio doctrine.

EVIDENCE

The directive requires candidate → evidence → validation → promotion.

ALTERNATIVES CONSIDERED

Direct agent writes to permanent knowledge.

WHY ALTERNATIVES WERE REJECTED

Too risky.

IMPLEMENTATION CONSEQUENCE

Knowledge is separated into candidate, validated, deprecated, and must carry provenance.

───

ADR-010: First slice uses HyperFrames only

DECISION

The first vertical slice uses HyperFrames as the only active renderer.

WHY

The core loop must be proven before adding Fusion, Resolve automation, Remotion expansion, and 3D.

EVIDENCE

The directive requires a minimum viable vertical slice.

ALTERNATIVES CONSIDERED

Build all renderer adapters simultaneously.

WHY ALTERNATIVES WERE REJECTED

Too much surface area before the core loop works.

IMPLEMENTATION CONSEQUENCE

Fusion/Resolve/Remotion adapters may be stubbed, but the first end-to-end production path must use HyperFrames.

npm workspaces policy

Use npm workspaces only where a local package boundary is genuinely useful.

Examples:

text
runtimes/hyperframes/package.json
runtimes/remotion/package.json
core/package.json


Do not create package boundaries merely for folder organization.

Node resolution strategy

Node’s documented module resolution allows a file in:

text
projects/acme-project/source/foo.ts


to resolve packages from:

text
MOTION-STUDIO/node_modules


because Node searches upward through parent directories.

Therefore projects can import shared dependencies without local installs.

Project-specific dependency exceptions

A project may require an exception only if:

1. a renderer requires an incompatible version;
2. a native module cannot be shared;
3. a client-specific integration requires isolation.

Exception format:

yaml
# projects/<project>/overrides/dependencies.yaml
schemaVersion: 1
kind: DependencyOverride
project: acme-premium-opening
reason: "Client requires pinned remotion version for legacy template."
override:
  package: remotion
  mode: isolated
  location: runtimes/remotion-client-acme


The default remains shared dependencies.

Preflight dependency policy

Do not run destructive install commands automatically.

Forbidden as routine preflight:

bash
npm ci
rm -rf node_modules


Allowed read-only checks:

bash
node -v
npm -v
npm ls --depth=0


Repair only when explicitly approved:

bash
npm install --no-audit --no-fund --prefer-offline


If lockfile mismatch is detected:

1. report mismatch
2. show affected packages
3. require human approval before modifying lockfile
4. use npm install --package-lock-only only after approval

MOTIONSPEC

MotionSpec is the structured creative contract.

It is not renderer-specific.

It is not a raw keyframe list.

It expresses:

• intent
• hierarchy
• beats
• objects
• relationships
• motion characteristics
• constraints
• negative instructions
• style

MotionSpec V2 schema, condensed TypeScript

ts
export type MotionSeverity =
  | "none"
  | "subtle"
  | "low"
  | "medium"
  | "strong"
  | "high";

export type MotionTempo =
  | "very-slow"
  | "slow"
  | "medium"
  | "fast"
  | "very-fast";

export type MotionEnergy =
  | "restrained"
  | "balanced"
  | "dynamic"
  | "aggressive";

export interface TimeRef {
  frame?: number;
  second?: number;
  percent?: number;

export interface DurationRef {
  frames?: number;

}

export interface Beat {

    | "story"

    | "visual"
    | "impact"
    | "anticipation"
    | "transition"
    | "hold";

  weight?: number;
  description: string;
}

export interface SemanticObject {
  id: string;

    | "primary_information"

    | "text"

    | "image"
    | "video"
    | "group"
    | "camera"
    | "layer";

    x?: number;
    y?: number;

}

export interface RelationshipIntent {
  id: string;

    | "follows"
    | "reacts"

    | "echoes"

export interface MotionEventIntent {

  };
}

MOTION IR

Motion IR is the canonical resolved representation.

It is still renderer-independent, but it is more machine-executable than MotionSpec.

It resolves:

• beats into frames
• durations into frames
• relationships into delays/constraints
• semantic behavior into curve profiles
• objects into scene graph nodes
• constraints into warnings and guards

Curve resolution process

The curve resolver must not use a fixed map like:

text
cinematic → power3.inOut


Instead:

text
MotionSpec behavior
→ normalized semantic values
→ attack/recovery envelope
→ overshoot/settle model
→ renderer capability check
→ resolved curve implementation


Example:

yaml
behavior:
  anticipation: medium
  impact: strong
  compression: high
  overshoot: controlled
  settle: soft

semantic:
  acceleration: 0.78
  deceleration: 0.62
  anticipation: 0.45
  impact: 0.82
  compression: 0.74
  overshoot: 0.35
  damping: 0.68
  stiffness: 0.56
  softness: 0.48
  snap: 0.41
  continuity: 0.72


The resolver may produce:

• GSAP keyframes
• GSAP standard ease
• cubic-bezier
• spring parameters
• renderer spline data

depending on renderer capabilities.

If the renderer cannot express the curve faithfully, the IR must record a warning and choose the closest stable approximation.

RENDERER CONTRACTS

All renderers implement an adapter contract.

ts
export interface RendererCapabilities {
  id: string;
  name: string;
  supports: {
    d2: boolean;
    d3: boolean;
    dom: boolean;
    svg: boolean;
    react: boolean;
    nodes: boolean;
    expressions: boolean;
    splines: boolean;
    particles: boolean;
    camera: boolean;
    dataDriven: boolean;
    deterministicSeek: boolean;
    alpha: boolean;
    audio: boolean;
  };
  maturity: "production" | "beta" | "stub";
}

export interface PreflightResult {
  ok: boolean;
  warnings: string[];
  errors: string[];
  version?: string;
  capabilities?: RendererCapabilities;
}

export interface CompilationResult {
  ok: boolean;
  outputDir: string;
  entrypoint?: string;
  warnings: string[];
  artifacts: string[];
}

export interface RenderResult {
  ok: boolean;
  outputFiles: string[];
  logs: string[];
  warnings: string[];
  deterministicNotes: string[];
}

export interface RendererAdapter {
  id: string;
  capabilities(): RendererCapabilities;
  preflight(): Promise<PreflightResult>;
  compile(ir: MotionIRV1, projectDir: string): Promise<CompilationResult>;
  render(compiled: CompilationResult): Promise<RenderResult>;
  inspect(render: RenderResult): Promise<Record<string, unknown>>;
}


Renderer selection

Renderer selection uses:

1. MotionSpec renderer preference
2. renderer capabilities
3. project overrides
4. client style constraints
5. availability from preflight
6. historical stability from knowledge base

Do not select a renderer merely because it is available.

HYPERFRAMES

Role

HyperFrames is the first production renderer.

It owns:

• HTML/CSS/media-to-video rendering
• deterministic seek/render pipeline where supported
• CLI-based preview/render/lint where available
• browser/FFmpeg execution details

Our studio owns:

• creative semantics
• MotionSpec
• Motion IR
• style intelligence
• renderer selection
• QA
• knowledge

Integration rule

Do not reimplement HyperFrames.

text
Motion IR
    ↓
HyperFrames adapter
    ↓
real HyperFrames project/files
    ↓
HyperFrames CLI
    ↓
MP4 / preview / lint output


Capability probe

Before first use, OpenCode must run:

text
runtimes/hyperframes/capability-probe.ts


The probe must discover:

• installed HyperFrames version
• CLI existence
• available commands
• init command
• preview command
• render command
• lint command
• output options
• configuration file format
• deterministic flags if available

The probe writes:

text
runtimes/hyperframes/capability-report.json


Do not hardcode unverified CLI flags in production code.

HyperFrames adapter behavior

The adapter must:

1. read Motion IR
2. generate a HyperFrames-compatible scene under:

text
projects/<project>/generated/hyperframes/<shot>/


1. write deterministic assets: 
◦ HTML/CSS
◦ scene script
◦ asset manifest
◦ seed config

1. invoke HyperFrames through verified CLI surface

1. collect: 
◦ render output
◦ logs
◦ warnings
◦ lint output

Determinism rules for HyperFrames

Generated scenes must:

• use seed-based randomness only
• avoid Math.random()
• avoid Date.now()
• avoid timers for animation logic
• use frame/beat-driven animation
• declare fonts explicitly
• use local assets
• record renderer version and dependency versions

Fallback

If HyperFrames is unavailable after capability probe:

1. stop production
2. produce deviation report
3. optionally use legacy internal renderer only if explicitly approved

Do not silently fall back to a different renderer.

GSAP

GSAP is not the source of truth.

GSAP is an execution capability.

Use GSAP where:

• DOM/GSAP choreography is needed
• timeline control is valuable
• HyperFrames-generated scenes benefit from GSAP animation
• complex stagger/overlap/follow-through is needed

GSAP integration must go through the curve resolver.

Forbidden:

text

Required:

text

→ semantic curve
→ GSAP-compatible curve/keyframes


GSAP timelines generated by the studio must be:

• paused
• seekable
• deterministic
• frame-resolved
• constructed from Motion IR

REMOTION

Remotion remains a valid renderer adapter, but it is not the universal default.

Use Remotion when:

• content is data-driven
• components repeat structurally
• React component reuse is valuable
• props determine layout/content
• template variants are required

Do not choose Remotion solely because React is familiar.

↓

yaml

project: acme-premium-opening
shot: shot-001

  The opening needs to feel more premium and restrained.
  Keep the composition but make the impact 20% heavier
  and let the typography breathe longer.
interpretation:
  - path: style.restraint
    op: increase
    amount: 0.1
  - path: events.title-impact.behavior.impact
    op: increase
    amount: 0.2
  - path: beats.beat-type-breathe.duration.seconds
    op: increase
    amount: 0.4
  - path: events.title-impact.timing.recovery
    op: set
    value: slower

  - "Do not change composition."
  - "Do not add decorative elements."


Patch rules

A revision patch must:

1. name the smallest affected artifacts
2. avoid rewriting the whole scene
3. preserve unchanged timing
4. preserve unrelated layout
5. preserve approved motion
6. update MotionSpec/Motion IR before renderer code where possible
7. rerun QA
8. record decision

If a requested change affects more than 40% of the scene, the system must request a new scene plan instead of silently rewriting.

Mitigation:

Risk: agents promote bad lessons.

• human promotion

Risk: studio becomes hard to install.

Mitigation:

• shared root dependencies
• explicit exceptions
• preflight repair approval

Risk: same input produces slightly different pixels.

Mitigation:

• separate logical determinism from pixel equality
• record environment/version data
• avoid promising pixel-identical output unless verified

Risk: knowledge gets dumped into prompts.

Mitigation:

• scoped skills
• artifact-based context
• selective loading

FINAL IMPLEMENTATION RULES

OpenCode must obey these rules while building the studio.

1. Do not reimplement existing infrastructure unnecessarily.
2. Do not invent renderer APIs.
3. Do not use destructive dependency commands automatically.
4. Do not let renderers become the source of truth.
5. Do not allow agents to mutate permanent knowledge without promotion.
6. Do not create per-project dependency trees by default.
7. Do not replace creative judgment with generic motion.
8. Do not treat technical success as creative success.
9. Do not rewrite scenes when a localized patch is sufficient.
10. Do not proceed past unverified external capabilities without a deviation report.

The studio is considered successful when:

text
the human can direct,
the agents can produce,
the system can validate,
the knowledge can accumulate,
and the output improves over time
without the human becoming a repair technician.
